# Plan Stage Request Receipts Correction Brief

- **Observed failure:** a Plan synthesis transition reserves both Builder and Reviewer Seats, but its saved artifact cannot distinguish a Reviewer that was merely reserved from one whose provider request started and then lost its result. Interrupted usage is therefore either absent or easily mistaken for zero.
- **User artifact:** preserve the Plan, accepted days, stage identity, request ID, requested output cap and the strongest truthful usage state available. Never store credentials, raw provider output or private reasoning.
- **Smallest hypothesis:** each paid Plan stage needs a persisted lifecycle receipt independent of the enclosing two-Seat transition. A `started` receipt with unknown finish and usage, emitted before provider invocation and replaced in place by the terminal receipt, is enough to separate not-started from started/unknown.
- **Change boundary:** extend `PlanAttempt.outcome` with `started`; add deterministic attempt upsert by request ID plus stage; emit and save a started Builder/Reviewer checkpoint before its `streamProvider` call; replace that same receipt on accepted, rejected or provider-error completion. Keep at most four terminal/current receipts under the existing cap.
- **Acceptance:** legacy artifacts still parse; malformed started receipts fail; started receipts show unknown usage rather than zero; terminal replacement creates no duplicate; Builder start precedes Builder provider invocation; Reviewer start exists only after Builder acceptance and precedes Reviewer invocation; a provider failure replaces started with `provider_error`; history round-trips the lifecycle state.
- **Cost and stop boundary:** zero real provider calls, no model/prompt/reasoning/output/budget/retry changes, no legacy migration and no generic billing ledger. Application estimates remain advisory and provider invoices remain authoritative. Stop after offline build/tests/lint/type checks and bilingual documentation.

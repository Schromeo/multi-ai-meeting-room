# 开发校正循环

状态：强制执行
日期：2026-08-27

## 目的

这份文档用于防止可靠的工程实现逐渐偏离真正有用的产品结果。协议跑完、parser 通过、transcript 漂亮或模型输出更长，都不能证明用户得到了更好的结果。

每个实现里程碑、付费评测和重要恢复尝试都必须经过这套校正循环。当证据否定当前设计时，下一步应修复已证明的最小原因，而不是直接增加轮数、Agent、输出 token、界面或通用基础设施。

## 当前诊断

下方审计记录较早的失败基线，不代表要重开已完成工作。当前Plan证据及逐项状态以[Plan问题清单](PLAN_ISSUE_REGISTER.md)为准；每次纠错先对照清单和最新开发日志。

当前应用正在成为可靠的会议控制平面，但还不是可靠的任务交付系统。最近的 Review 和 Decide / Plan 测试暴露了三个主因：

1. 通用 Discuss 协议正在承担本应由任务专属 Artifact、角色、阶段、上下文策略、Human Gate 和 rubric 完成的 Task Pack 工作。
2. 参与模型只提交简短意见，而不是可独立采用的 Artifact 材料，导致最终 Synthesizer 仍要单独发明大部分交付物。
3. 复杂交付物仍由一次自由文本响应生成，并在付费调用后才验证；遗漏代价高，恢复粒度也过粗。

### 产品与协议问题

- Review 和 Plan 仍有部分工作通过通用 proposal、cross-review、memo 顺序表达。
- Plan M2.13 尚未开始；当前 Plan 路径只是进入证据，不是完成的 Plan Task Pack。
- 精简 Canonical Meeting State 适合 Claims 和 Disputes，不适合几十条详细 Artifact 记录。
- 共享 recovery 额度可能被较早的格式错误消耗，最终 Artifact 因此没有定点恢复机会。
- Human Gate 还不能在不重开整轮讨论的情况下编辑、锁定或修复单个 Plan 单元。
- 固定全员阶段即使只剩一个明确问题，也会增加调用和上下文成本。

### Prompt 与契约问题

- Proposal 和 review 被有意压短，但最终 Synthesizer 却要根据这些摘要构建大型详细 Artifact。
- 通用角色 prompt 没有把 Artifact 的章节或记录分配给不同参与者。
- 禁止引入 canonical state 之外 named examples 的 Review 指令适合防止无依据事实，却会压制 Plan 所需的具体示例。
- 一次 synthesis 同时承担规划、内容选择、算术、完整性、Markdown 结构与 JSON 转义。
- 自由文本生成后才由存在性 validator 检查；它们不能证明事实、算术或教学质量正确。
- 增加输出上限没有解决遗漏。Smoke 007 在远低于上限时结束，仍缺少 Day 2。
- 语言一致性、完整性与提交前自检仍主要依赖 prompt。

### 角色与模型问题

- 通用 Strategist、Critic、Technical Lead 和 Synthesizer 不能保证任务化覆盖。
- 复用作者模型做 Synthesizer 会产生锚定，并削弱独立判断。
- 供应商或模型不同不代表认知一定不同；多个模型曾重复同一个错误日期推断，也共同漏掉明确指标约束。
- 在小型隔离 schema 中表现稳定的模型，进入完整房间长上下文后仍可能违反同一契约。
- Model discovery 不代表可选 reasoning 或 thinking 参数一定兼容。
- 更多推理不能保证结构化输出，只可能改善部分语义权衡，同时提高费用和延迟。
- 尚未完成强单模型、当前多模型、较强 Artifact Builder 与分阶段 reasoning 设置的受控比较。

### 工程与体验问题

- 很多验证发生在供应商已经生成并计费之后。
- 失败原始候选与字段级诊断没有始终保留，无法精确修复。
- Transcript、Canonical State 和恢复上下文曾出现分叉或废弃重复卡片。
- 切换房间、刷新或丢失 session 凭证，可能在页面无法完整拥有的边界中断付费工作。
- 原始流式 JSON 对用户不友好，完全缓冲又会造成长时间无解释等待。
- 即使只有两行 Artifact，完整 Review 也存在明显固定调用和上下文开销。
- 应用成本估算适合预算控制，但不是供应商权威账单。

### 不能重复的评测错误

- 能用固定 Stage Replay 隔离失败子阶段时，不要重跑整个房间。
- 不要在一次对照中同时更换 objective、Artifact 契约、输出上限、模型和 validator。
- 没有证明截断是原因前，不要提高输出上限。
- 没有保存 golden Artifact、任务 rubric 和单模型 baseline 前，不运行完整 benchmark。
- 不把协议机械成功称为 Artifact 成功。
- 没有找出 baseline 漏掉、但交叉审阅独有且被接受的改进时，不宣称多模型价值。
- 用户 Artifact 仍失败时，不先围绕现有流程做成本微优化。

## 强制 Correction Brief

开始实现前，必须在当前里程碑、issue、评测记录或开发更新中回答：

1. **已观察失败：** 哪个真实用户案例或保存 fixture 在哪个阶段失败？
2. **用户 Artifact：** 用户最终应得到什么可直接采用的结果？
3. **Baseline：** 一个强单模型或当前保存版本会产生什么？
4. **最小假设：** 这次修改只验证哪个原因？
5. **预期信息增量：** 每个新增付费调用或模型角色为什么必要？
6. **验收检查：** 哪些确定性检查和人工 rubric 定义成功？
7. **成本边界：** 允许多少调用、token、延迟、美元和阅读负担？
8. **停止条件：** 什么结果会结束、回退、简化或转向这条分支？

如果无法回答，下一步只能是文档、fixture 或 baseline，不得扩建实现。

## 开发 Gates

### Gate 0：目的

- 写明当前 Task Pack 和里程碑。
- 把修改链接到一个已观察的用户失败。
- 拒绝没有明确消费者的通用基础设施工作。

### Gate 1：Artifact

- 在调 prompt 前定义 Artifact schema 和用户验收 rubric。
- 将精简模型工作状态与详细用户交付物分开。
- 可独立失败的单元优先使用可寻址 Record，而不是一次自由文本响应。

### Gate 2：职责

- 每个模型必须对 Artifact 或验证做出独特且可检查的贡献。
- 格式、计数、算术和状态修改交给应用代码。
- 只有语义判断确实需要时，才使用更强或独立模型。

### Gate 3：本地证据

- 先加入确定性 fixture 和 validator。
- 测试缺失、重复、畸形、无依据和部分 Artifact 单元。
- 使用 durable receipt 保留已经完成的有效子阶段。

### Gate 4：付费证据

- 遵循：本地测试 -> 单阶段 replay -> 短合成 smoke -> 真实 benchmark。
- 不原样重试失败输入。
- 每次只比较一个变量，并保留原始失败诊断。

### Gate 5：产品结果

以下维度必须分别打分：

- 机械完成；
- 语义或事实可靠性；
- Artifact 完整性与可用性；
- Human Gate 的可编辑性与采用结果；
- 延迟、费用和阅读负担；
- 相比 baseline，交叉审阅独有的改进。

一个维度通过不代表其他维度通过。

### Gate 6：方向决定

里程碑结束时必须明确选择：

- **继续：** 证据支持下一条有限切片。
- **修复：** 一个隔离失败已有明确修复和测试。
- **简化：** 多模型或协议开销不值得。
- **删除：** 功能没有产生被接受的用户价值。
- **暂缓：** 需求可能成立，但不在当前关键路径。

宣布完成前，更新开发日志、发生状态变化时的路线图、形成长期选择时的决策记录、AI 交接及其中文镜像。

## 已批准修复路径

1. 冻结新的通用编排功能和进一步完整付费 Plan 重跑。
2. 只完成 M2.11 中评测真正需要的采用路径：Verifier v2 证据、逐项 Change 编辑、不可变批准和保存 baseline；不打磨无关 Review 基础设施。
3. 完成 M2.12 Review 对照，决定现有协议中哪些组件值得复用。
4. M2.13 从 golden 受约束计划 fixture 与 rubric 开始；先定义结构化、可按日期寻址的 `PlanArtifact`，再改 prompt。
5. 给 Plan 任务化角色分配独立有用的职责；使用单独 Artifact Builder 和语义 Auditor，不再要求简短通用 turn 支撑一次英雄式 synthesis。
6. 加入确定性的完整性、工作量、身份与算术检查；具体 LeetCode 元数据需要可靠题库来源。
7. 持久化有效 Plan 单元，只修复缺失或无效单元，并为各阶段分别设置 recovery 预算。
8. 本地结构稳定后，再比较强单模型 baseline、较强最终 builder、有限多模型流程与分阶段 reasoning 设置。
9. Artifact 流水线可靠后再改善进度展示：显示阶段、目标、已耗时间和已完成 Artifact 单元，不流式展示原始 JSON。

下一次代码修改必须推进其中一项并写明退出条件，不能试图一次解决所有问题。

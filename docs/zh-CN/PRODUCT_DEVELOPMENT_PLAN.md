# 产品开发计划：由人主持的 Multi-AI 工作空间

状态：已批准
批准日期：2026-09-18

项目所有者已于 2026-09-18 批准本方向。[详细开发里程碑](DEVELOPMENT_MILESTONES.md)是分阶段执行顺序的 canonical 文档。历史实现与评测证据继续有效；本计划只改变前向优先级，不重写过去结果。

## 核心主张

打造一个由人主持的 Multi-AI 工作空间：它可以从普通聊天开始，在单一答案不够时升级为多个模型的独立挑战，随后再按任务需要进入审阅、创作、研究、游戏或受控执行。

它不只是专业 Review 工具，不是多模型答案陈列墙，也不是自治 AI 公司。长期承诺是：

> 当一个答案不够时，就 Ask the Room。保留有价值的差异，让人来主持，并把差异转化为更好的对话、产物、决定或经过验证的行动。

终点可以很宽，但最初反复发生的动作必须很窄：**Ask the Room**。

## 为什么现在要重排计划

### 已观察到的错位

当前路线把工程注意力收束到 Review 和产物质量，这个纠偏本身是正确的；但现有排期容易让人误以为“专业文档审阅”就是产品边界。真正的产品还应覆盖日常聊天、娱乐、头脑风暴、创作、研究、游戏，以及未来通过 Codex 或 VS Code 进入项目级 Agent 工作。

### 必须保留的已有资产

- 真实 OpenAI、Anthropic、Gemini 适配器；
- 会话级 BYOK，以及 Connection、Model、Role、Seat；
- 独立提案、交叉审阅、定向争议、预算、恢复和 Human Gate；
- 本地优先的 Room、Event、State、Artifact、Usage 持久化；
- Review 版本、来源关联修改、验证和不可变批准；
- 结构化 Plan 生成、局部恢复、审阅、修改和精确批准。

### 当前基线

现在的产品要求用户先配置较深的 Room，价值才开始显现。Review 的 Artifact 机制最完整，但比较优势仍未证明；通用 Discuss 功能很强，却不适合作为日常用户的默认入口。

### 最小计划假设

一个升级动作可以连接日常产品与专业产品：

1. 从普通回答或用户提供的 Artifact 开始；
2. 只有在多样性有价值时才调用 **Ask the Room**；
3. 展示真正影响结果的差异，而不是几份完整 transcript；
4. 人可以停止、提出一次定向追问，或把工作升级到更深的 Task Pack。

### 预期信息增益

这个顺序无需先建完整平台，就能分别验证两个问题：

- **习惯价值：** 普通用户会不会反复主动请求第二视角？
- **信任价值：** 结构化 Pack 能否产出强单模型漏掉、且用户愿意采用的改进？

### 停止条件

如果 Quick Council 大多只产生重复文字，增加的速度与阅读负担超过价值，或用户不会再次主动调用，它就只保留为可选对照动作，不成为默认体验。如果 Review 无法相对强单模型产出被接受的重要改进，就把它简化成“单模型主写 + 可选独立挑战者”，而不是继续扩建协议。

## 产品形态

### 一个产品，四种交互深度

| 深度 | 用户意图 | 默认行为 | 输出 |
| --- | --- | --- | --- |
| Solo | “现在就帮我。” | 一个模型，普通聊天 | 直接回答 |
| Quick Council | “从多个角度检查一下。” | 两到三个独立视角，不进行完整辩论 | 差异地图与建议下一步 |
| Deep Council | “这件事重要，请挑战关键分歧。” | 有限交叉审阅、Chair 检查点、可选定向轮次 | 决定、产物或未解决问题集 |
| Task Pack | “针对这个任务使用正确流程。” | Pack 专属角色、真实性策略、状态、产物和 Human Gate | Review、Plan、研究简报、创作、游戏状态或行动结果 |

用户不需要先理解这些架构才能获得价值。深度应逐步升级：一个答案可以升级为 Council，一个 Council 也可以在不重开任务的情况下升级为 Pack。

### 切口是一种时刻，而不是一种职业

第一切口不是“会审 PRD 的专业人士”，而是不断出现的这个时刻：

> 我已经有一个答案、想法、选择或 Artifact，但我不想让单个模型的盲点决定结果。

这个时刻既出现在日常聊天、占星和反思型娱乐、购物、旅行、写作和脑暴里，也出现在文档审阅、公司分析、金融情景和软件开发中。最终人群可以很广，但共同的用户动作足够窄。

### 一个内核，多种真实性模式

不同体验不能共用一条“所有人说一遍，然后总结”的万能协议。它们可以共用基础设施，但每个 Pack 必须声明如何判断真实性和成功。

| 真实性模式 | 示例 | 必需行为 |
| --- | --- | --- |
| 对话型 | 日常聊天、建议 | 暴露假设，不制造确定性 |
| 娱乐型 | 占星、角色扮演 | 明确说明是解释性或虚构体验，优化连贯性与趣味 |
| 发散型 | 头脑风暴 | 批判前先扩大有效差异，保留离群好点子 |
| 证据约束型 | 文档或项目审阅 | Finding 绑定来源，区分证据与推断 |
| 研究／预测型 | 公司环境、金融情景 | 引用带日期来源，区分事实、假设、情景与不确定性 |
| 规则约束型 | 桌游与模拟 | 由应用掌管合法动作、私有状态、随机性和回放 |
| 执行型 | 代码或工作区变更 | 权限限定、隔离工作、测试、批准、回执和回滚边界 |

娱乐产物绝不能借用证据型 Review 的权威语气。研究或金融情景也绝不能包装成保证预测。在任何模式中，多模型同意都不等于验证。

## 共享架构

### Council Kernel

Council Kernel 是可复用的产品内核：

- Connection、Model、Role、Skill、Seat 组合；
- 独立上下文与选择性共享上下文；
- Human Chair 控制、预算、停止规则与批准；
- 请求回执、中断恢复和防重复调用；
- Room、Event、State、Artifact、Version、Usage 持久化；
- 保留分歧和不确定性；
- 来源 lineage、权限边界和导出；
- 从 Solo 升级到 Quick Council，再升级到更深 Pack。

当前实现已经具备内核的大部分能力。只有活动产品切片需要某个边界时才抽取或泛化；Rule of Two 继续有效。

### Task Pack 契约

只有两个经过验证的 Pack 都需要同一边界后，才可以形成可复用 Pack contract：

- 入口意图和输入 schema；
- 推荐 Seat 与 Role 组合；
- 真实性模式和来源策略；
- 阶段协议和上下文可见性；
- Pack 本地状态和 Artifact schema；
- Human Gate 与权限级别；
- 评测 rubric、预算和停止规则。

Pack 不是提示词预设，而是一套有限行为和 Artifact 契约。

### 产品表面

- **Web：** 主要的聊天、Room、Artifact、历史和 Pack 发现界面。
- **VS Code／Codex：** 未来的项目上下文界面；先只读，再提案，最后才在批准后执行。
- **文档和项目工作区：** 它们是来源与 Artifact，不会自动变成授权。
- **本地 Connector：** 未来与托管控制平面分离的执行平面。

## 开发策略

### 两条价值线，一条构建队列

产品同时需要两类证据：

- **习惯线：** Quick Council、Explore、娱乐、Create、Play 验证使用频率、趣味和传播。
- **信任线：** Review、Research、Plan、Project Room 验证准确性、采用与依赖意愿。

这不意味着同时开启两条失控的实现线。任何时候只有一个有限切片处于活动状态；两条价值线交替获取证据，只有经过真实复用才进入 Council Kernel。

### 实验室

一些小实验可以探索宽愿景，但不进入关键路径：

- 一个占星或反思型娱乐模板；
- 一个 Multi-Agent 桌游原型；
- 针对已保存编码任务的一次提示词／上下文审计。

每个 Lab 都有时间上限，与 Shared Core 隔离，不作平台声明，并以 Promote、Repeat 或 Archive 结束。只有用户完整使用并主动想再次使用，实验才有资格成为 Task Pack。

## 里程碑顺序

以下是证据 Gate，不是日历承诺。批准本计划不等于授权付费模型调用、对外发布或 Execute 行为。

### DP-0 - 产品真实性与第一分钟体验

**目标：** 在新增协议前，让现有产品容易理解，也能安全地体验。

**交付：**

- 对齐产品身份、版本／状态文案和各模式默认 Objective；
- 在信息架构中明确 Solo、Quick Council、Deep Council、Pack；
- 一个可用 Connection 就能开始 Solo；只有用户升级到 Ask the Room 时才要求另一个独立 Seat；
- 增加无需凭证的回放／Demo，展示一个已有的有效多模型结果；
- 先增加 Artifact 和 Room 导出，再考虑账号同步；
- 在使用工作区付费 key 公开部署前，关闭公共端点的认证／限流歧义；
- 让 CI、TypeScript 环境声明、包管理器策略和源码文本测试可移植；
- 不修改现有 Review 与 Plan 历史记录。

**退出标准：** 新用户从第一屏就能说明产品是什么，无需提供 key 就能查看代表性结果；进入某模式不会继承其他模式的 Objective；结果可以导出；build、lint、测试和 type check 都有明确、真实的状态。

**非目标：** 为视觉而重做视觉、新 Agent、新供应商、账号同步、计费或通用插件系统。

### DP-1 - Quick Council MVP：Ask the Room

**目标：** 用最轻、但仍有价值的模型差异验证日常入口。

**交付：**

- 以普通单模型聊天作为最低摩擦入口；
- 从回答、问题或选中上下文发起一次 **Ask the Room**；
- 把已有回答作为第一个视角，再加入一到两个独立提示的 Challenger，之后才允许共享总结；
- 紧凑差异地图：共识、关键差异、隐藏假设和一个建议下一步；
- Chair 动作：接受一个方向、提一次定向追问、进入 Deep Council 或停止；
- 升级前显示最大调用次数与建议成本；
- 默认不启用 Observer，也不自动进入第二轮。

**评测集合：** 十二个保存案例，覆盖日常选择、反思／娱乐、创意发散和实用规划；每个案例都有强单模型基线。

**初始退出目标：** 至少一半案例出现用户接受、且不与基线重复的有效增量，并改变结论、约束或下一步；无需打开每份全文即可读懂差异地图；不受支持的事实仍明确带有不确定性；至少五名试用者会在第二个任务上再次主动调用 Ask the Room。

**停止规则：** 如果有效独特增量低于三分之一，或额外阅读／成本持续不可接受，就只保留可选 compare card，不把它设为首页默认。

### DP-2 - Review 作为信任 Pack

**目标：** 用当前最完整的 Artifact 管线验证结构化挑战是否能赢得信任。

**交付：**

- 不重生成已保存有效产物，只完成 saved-artifact Reviewer 边界；
- 不看 transcript 也能理解来源关联 Finding、Change、验证范围和 Human Gate；
- 在固定 benchmark 类别上运行强单模型、手工双模型、结构化 Review 三条匹配路径；
- 增加采用最终 Artifact 所必需的导入／导出；
- 把 Keep original 保留为一等、成功的人工结果。

**退出标准：** 至少两个 benchmark 类别中，结构化 Review 产出强单模型 Artifact 没有、且被人接受的重要改进；同时 rejected Finding、成本、延迟和阅读负担满足冻结 rubric。只有机械跑通不算通过。

**停止规则：** 如果结构化路径不优于简单路径，就收缩为“一个 Author + 可选独立 Challenger”，只保留用户真正采用的 Artifact／Version／Human Gate 能力。

### DP-3 - Pack contract v1 与自适应首页

**目标：** 只整合 Quick Council 与 Review 已经共同证明的边界。

**交付：**

- 依据 Rule of Two 形成第一个可复用 Pack manifest 与 runtime 边界；
- 对话或 Council 可升级为 Pack，而不复制整段 transcript；
- Pack 专属真实性模式、上下文策略、Artifact、Human Gate、预算与评测元数据；
- 首页围绕 Chat、Ask the Room、Drop an Artifact、Browse Packs 组织；
- 支持保存模板，但不建设公开 marketplace。

**退出标准：** Quick Council 与 Review 共用边界但不丢失各自协议；第三个内部 Pack 原型无需修改供应商或持久化基础。

### DP-4 - Explore 与 Create

**目标：** 证明同一产品不仅能纠错，也能承载趣味和创意连续性。

**交付：**

- Explore Idea Board：发散角色、聚类、保留离群好点子、人工筛选；
- Create：一个指定 Author、编辑角色、版本化章节、有限 Artifact Memory；
- 一个明确标注的娱乐模板，例如反思型占星；它属于 Explore 体验，不充当事实权威；
- 可分享、可导出的结果。

**退出标准：** Explore 产生单模型基线遗漏、且用户愿意保留的点子；Create 改善被选 Artifact 而不抹平原有声音；用户能够理解娱乐模式的真实性边界。

### DP-5 - Research 与情景预测

**目标：** 在来源和 Artifact 边界可靠后，再引入外部事实环境。

**交付：**

- 检索 Connector、带日期来源保存、Citation 检查和 freshness；
- 并行来源调查，以及明确的合并与矛盾处理；
- Claim 状态：supported、contradicted、inferred、outdated、unresolved；
- 公司／环境与金融情景模板，分开事实、假设、概率、触发器和反证；
- 不自动交易，也不自动执行有后果的外部动作。

**退出标准：** 被采用简报里的每个重要事实 Claim 都有可检查的来源状态；冲突证据保持可见；Room 能诚实输出“未解决”，而不是制造共识。

### DP-6 - 从 Play Lab 到 Play Pack

**目标：** 验证模型差异能否形成可回放的社交体验，而不是即兴规则漂移。

**交付：**

- 只做一个游戏；
- 应用拥有确定性规则和合法动作；
- 带可见性测试的公开／私有 Seat 状态；
- 带种子的随机性、有限回合、人类 Host 控制和回放；
- AI 性格只负责表现，绝不拥有规则权威。

**退出标准：** 游戏在不泄露隐藏状态、不产生非法动作的情况下完成；回放可解释每次状态变化；用户愿意再玩。达到后才讨论第二个游戏或通用 game-pack 接口。

### DP-7 - 面向 Codex 与 VS Code 的 Project Room

**目标：** 在授予写权限前，先把 Council 变成项目级上下文和提示词优化层。

**交付：**

- 只读项目快照与用户选定的上下文范围；
- Planner、Context Critic、Builder、Reviewer、Tester 的独立职责和视图；
- 提示词／上下文审计，识别缺失约束、过期假设、无关上下文，并建议 context pack；
- 带测试与风险说明的 Plan 和 Patch proposal Artifact；
- Codex 与 VS Code 适配边界，不假设能读取它们的私有推理。

**退出标准：** 对已保存开发任务，Project Room 能改善任务表述，或发现原单 Agent 尝试遗漏的重要问题；同时不写入仓库，也不泄露无关文件。

### DP-8 - 受控 Execute

**目标：** 只有只读 Project Room 能稳定产出可靠计划和审阅后，才允许验证过的项目行动。

**交付：**

- 独立本地或隔离执行平面；
- 最小权限工作区范围与显式行动批准；
- Planner、Executor、独立 Reviewer、确定性 Tester 分离；
- 幂等回执、Patch 检查、回滚边界和最终 Human Gate；
- 不允许无人看管的递归 Agent 组织。

**退出标准：** 一个获批的有限任务产生可检查 Patch，通过声明的检查，真实报告失败，并且不会修改获批范围外的任何外部状态。

### DP-9 - 产品化与选择性扩张

**目标：** 只有能力已经证明重复使用或信任价值后，才增加 identity、加密同步、billing、collaboration、精选 Pack 分发和发布加固。

**退出标准：** v1 candidate 不保留任何只因工程沉没成本存在的功能；用户知道数据归属和谁支付调用费用；local-only 继续可用；权限、删除、恢复和发布 rollback 都经过测试。

## 产品与工程指标

### 习惯价值

- 获得第一个有用答案所需时间；
- Ask the Room 调用率和第二任务复用率；
- 用户保留的独特视角；
- 结果保存、导出和分享；
- 阅读负担与放弃率。

### 信任价值

- 挑战路径独有、且被接受的重要改进；
- 不受支持、被拒绝和重复的 Finding；
- Artifact 采用率和人工编辑距离；
- 有来源 Claim 覆盖率和未解决风险可见性；
- 用户是否愿意在声明任务上依赖结果。

### 经济与运行价值

- 每个被采用结果的调用、Token、延迟和建议成本；
- 阶段回执和部分 Artifact 保留下来的失败付费工作；
- 不重复调用的恢复成功率；
- 本地存储／导出可靠性与隐私事故。

### 平台价值

- 经过验证的 Pack 数量，而不是提示词预设数量；
- 新 Pack 在不修改 Kernel 的情况下复用内核；
- 只有两个真实消费者出现后才提升的抽象；
- 权限或上下文边界回归；
- Lab 是否带证据进入 Promote、Repeat 或 Archive。

## 护栏

- 野心宽不等于同时实现所有方向。
- 默认使用能解决任务的最浅交互深度。
- 每次新增模型调用都要说明预期新增信息。
- 当分歧影响结果时保留分歧，但隐藏重复 transcript 体积。
- 真实性策略属于 Pack，并且对用户可见。
- 趣味 Pack 可以好玩，但不能冒充证据。
- 预测是带不确定性的情景，不是保证。
- Play 的规则和私有状态属于代码，不属于模型记忆。
- 项目访问从只读开始；写权限是以后单独、明确的权限跃迁。
- 没有两个经过验证的消费者，就不增加 Shared Core 抽象。
- 每个里程碑都可以以 Continue、Repair、Simplify、Archive 或 Defer 结束。

## 已批准方向

# 产品方向定稿

状态：已批准
日期：2026-09-18

## 为什么需要这份方向定稿

项目起点来自一个简单观察：单个模型常会过早接受一条看似合理的路径，而第二个独立获得任务的模型可能发现遗漏约束、无依据主张和更好的替代方案。产品应把用户手动复制、审阅、再复制的流程，变成有限、可检查的协作，并同时服务普通对话与有后果的工作。

v0.3 到 v0.10c 已建立可信工程基础：真实供应商适配、会话 BYOK、可复用 Seat、流式输出、本地持久化、结构化 Meeting State、人类 checkpoint、预算、中断恢复、可选 Observer，以及围绕 Dispute 的定向辩论。这些工作有价值，但基础设施成熟度已经超过“用户是否获得明显更好结果”的产品证据。

2026-08-25 的校正不是推倒重来：它停止基础设施优先扩张，强制现有基础交付用户可见 Artifact。2026-09-18 的所有者决定保留这套纪律，同时澄清更大的产品边界。Review 是第一个信任 Pack，不是整个产品；日常入口是从普通回答、想法、选择或 Artifact 发起更轻的 **Ask the Room** 升级。

## 北极星

> 当一个答案不够时，就 Ask the Room。保留有价值的差异，让人来主持，并把差异转化为更好的对话、产物、决定或经过验证的行动。

本产品不是模型切换器、并排答案列表、只面向专业人士的审计工具，也不是自治 AI 组织。长期价值来自这条改进链：

> Objective -> Sources -> Artifact -> Finding -> Objection -> Change -> Verification -> Human Decision

## 产品形态

它仍是一个产品。任务模式定义要完成什么工作；权限等级定义房间可以使用什么工具。

### 交互深度

- **Solo：** 一个模型和普通对话，提供最低摩擦答案。
- **Quick Council：** **Ask the Room** 增加一到两个独立提示的 Challenger，返回紧凑 Difference Map。
- **Deep Council：** 有限 cross-review、一个 Chair checkpoint；只有命名定向追问具有预期信息增益时才新增调用。
- **Task Pack：** 针对任务定义真实性模式、角色组合、上下文策略、状态、Artifact、Human Gate、预算和 rubric。

交互深度逐步升级。用户可把选中上下文从回答提升到 Council 或 Pack，无需重放整个 transcript，也无需重开任务。

### 任务模式

- **Review：** 根据目标和用户提供的来源，检查并修订已有产物。
- **Decide / Plan：** 比较路径，或生成带风险、成立条件和 checkpoint 的可执行计划。
- **Explore：** 在收敛前扩大可能性空间，包括脑暴和反思型娱乐模板。
- **Create：** 通过创作、编辑审阅和版本化修订，维护连贯的长篇产物。
- **Play：** 运行包含公共与私有 Seat 状态的规则模拟或游戏。它是未来实验 Pack，不是当前优先级。

### 权限等级

- **Discuss：** 只基于用户提供的上下文和持久化房间产物进行推理。
- **Research：** 检索来源、保存时效信息，并把主张标记为有支持、矛盾、推断、过期或未解决。
- **Execute：** 在隔离执行面使用已批准工具，并验证产生的状态变化。

任务模式与权限等级相互独立。Review 可以只用 Discuss，也可以启用 Research；Create 可以使用 Research；Play 可以调用确定性工具，但不会因此获得通用工作区权限。

## 共享核心与任务 Pack

开发由产品线驱动。一层精简共享核心支持多个纵向 Task Pack。

### 共享核心

- provider、model、Connection、Role、Skill 与 Seat 组合；
- 流式调用和验证后 Turn 呈现；
- room、event、state、artifact、version 与 usage 持久化；
- 预算、停止、中断、幂等和人工批准边界；
- 上下文策略和来源链；
- 协议运行与权限执行。

### Task Pack

每个 Pack 自己定义 agenda schema、推荐 Role Pack、阶段协议、新增状态、上下文策略、Artifact 类型、Human Gate 和评测 rubric。Task Pack 不重复实现供应商接入、持久化、计费边界或房间历史。

采用 **Rule of Two**：只有至少两个经过验证的 Task Pack 都需要一个抽象时，它才进入共享核心。此前保留在具体 Pack 内。

## 产品入口与第一个信任 Pack

**Ask the Room** 是日常使用的窄入口。它检验普通用户是否会主动寻找并重复使用独立第二视角，而无需承担完整 Meeting 的交互成本。已有回答是视角一；Challenger 在 Difference Map 前保持独立。

Review 继续作为第一个完整信任 Pack，因为它能直接检验差异化假设，并产生可与单个强模型比较的结果。现有 Review 证据与 Artifact 机制全部保留，但该 Pack 不再定义整个受众或首页体验。

第一版 Review 流程：

1. 人类提供目标、Artifact v1、参考资料和真实性边界。
2. 两到三个任务自适应审阅者独立检查。
3. 系统聚类重复 Finding，同时保留关键冲突。
4. 只有明确的高影响问题获得有限交叉审阅或定向辩论。
5. 指定 Editor 生成结构化 Change Set 和 Artifact v2。
6. 独立审阅者根据目标、来源和真实性边界核验改动部分。
7. 人类逐项接受、拒绝或编辑修改，之后才能批准不可变版本。
8. 房间发布简短摘要、详细产物、已接受 Change Set、未解决问题和用量。

首批 benchmark 是“简历对照职位描述”、产品或需求文档，以及技术计划。简历是有用 benchmark，不是永久市场边界。

## 后续顺序

已批准的前向顺序见[详细开发里程碑](DEVELOPMENT_MILESTONES.md)：

1. **DP-0：** 对齐产品和仓库真实性、首次使用信息架构、免凭证 Demo、导出、工程可移植性与公共 API 安全。
2. **DP-1：** 构建并评测 Quick Council／Ask the Room，作为日常窄入口。
3. **DP-2：** 完成有限 Review 证据，并根据匹配对照保留、简化或删除协议组件。
4. **DP-3：** 只从两个已验证消费者收束 Pack contract，再用第三个内部 Pack spike 证明。
5. **DP-4：** 加入 Explore 与 Create，以及一个明确标注的反思型娱乐 Lab。
6. **DP-5：** 加入带日期来源的 Research 与保留不确定性的公司／金融情景工作。
7. **DP-6：** 只有一个确定性、安全保护隐私、可回放的游戏通过后才把 Play 提升为 Pack。
8. **DP-7：** 为 Codex 与 VS Code 上下文／提示词审阅增加只读 Project Room。
9. **DP-8：** 只有只读项目证据、隔离权限、独立审阅、确定性检查和回滚齐备后，才增加受控 Execute。
10. **DP-9：** 只对有重复使用证据的能力增加 identity、sync、billing、collaboration 与精选分发。

历史 `M0` 到 `M5` 路线继续作为实现与证据账本，但不覆盖这套前向顺序。

## 多 Agent 边界

多个模型 Seat 不会自动变成自治 Agent。只有任务可以拆成独立有用的子任务、参与者需要不同工具或私有上下文、输出具有合并契约且结果可以验证时，才加入多 Agent 行为。

Review 首先使用有限模型角色和确定性编排。Research 可以增加 Lead Researcher、并行 Search Worker 和 Citation Checker。Execute 可以在隔离工作区中增加 Planner、Executor、Reviewer 和 Tester。当前产品不以通用自治 Agent 平台为前置条件。

## 方向校正

这些检查必须按照[开发校正循环](DEVELOPMENT_CORRECTION_LOOP.md)执行。每个实现切片在扩大代码工作前，都必须写明已观察失败、用户 Artifact、baseline、最小假设、预期信息增量、验收检查、成本边界和停止条件。

每个完成的产品里程碑必须回答：

1. 这次修改解决了哪个真实用户问题？
2. 用户最终获得了什么可使用的产物或决定？
3. 一个强模型是否能用更低成本得到同样结果？
4. 哪些关键发现明确来自独立交叉审阅？
5. 增加了多少成本、延迟、阅读负担和复杂度？
6. 如果证据不足，应删除或简化什么？

开发硬规则：

- 不连续进行两个纯基础设施里程碑。
- 每个产品里程碑以至少一个真实案例和保存的基线结束。
- 每个新增付费模型调用在实现前必须写明预期信息增量。
- 不为只有一个已验证使用者的需求创建共享抽象。
- 没有明确用例和 Human Gate，不扩大自治、权限、模型数量或轮次。
- 漂亮 transcript 或可靠状态机不等于更好的用户结果。
- 如果协议机械通过但 Artifact 失败，下一步应修复 Artifact 契约或任务职责拆分，而不是继续打磨通用编排。

## 成功证据

宽产品需要两种证据。**习惯证据**检验用户是否会为普通或有趣任务主动调用并重复使用独立视角；**信任证据**检验结构化挑战是否产生强单模型遗漏、且最终被接受的重要改进。两者都必须把成本、延迟和人工阅读负担保持在可接受范围。

至少跟踪：

- 交叉审阅独有且被接受的高影响修改；
- 错误、无依据或被拒绝的 Finding；
- 根据任务 rubric 得到的 Artifact 质量；
- 达到可采用结果所需时间和人工编辑量；
- 调用、token、延迟和提示性费用；
- 协调、上下文丢失、同质化或“模型一致但没有证据”导致的失败。
- Ask the Room 调用、第二任务复用和用户保留的独特视角；
- 保存、导出或分享的结果，以及阅读负担造成的放弃；
- Pack 复用是否避免了推测性 Shared Core 扩张；
- Research、Play、Project、Execute 中的权限、隐私、规则或上下文边界失败。

不能改善这些证据的功能应被简化、改成可选或删除。

## 明确延后

延后公开 Pack marketplace、任意远程 Pack 代码、广泛自定义 endpoint、默认付费 Observer、没有命名消费者的语义路由或 embedding 基础设施、一个游戏通过前的通用游戏引擎、无限长期记忆、所有权规则前的账号协作、自动金融行动与不受限执行。Lab 可以探索占星、游戏和编码上下文批判，但在 promotion Gate 通过前不进入 Shared Core，也不宣称正式产品状态。

# 产品方向定稿

状态：已批准
日期：2026-08-25

## 为什么需要这份方向定稿

项目起点来自一个简单观察：单个模型常会过早接受一条看似合理的路径，而第二个独立获得任务的模型可能发现遗漏约束、无依据主张和更好的替代方案。产品应把用户手动复制、审阅、再复制的流程，变成有限、可检查的协作。

v0.3 到 v0.10c 已建立可信工程基础：真实供应商适配、会话 BYOK、可复用 Seat、流式输出、本地持久化、结构化 Meeting State、人类 checkpoint、预算、中断恢复、可选 Observer，以及围绕 Dispute 的定向辩论。这些工作有价值，但基础设施成熟度已经超过“用户是否获得明显更好结果”的产品证据。

本次校正不是推倒重来。停止扩建通用编排器，用现有基础完成用户可感知的 Artifact 工作流。

## 北极星

> 把一个重要问题或产物交给多个独立 AI 视角，让它们挑战关键差异，并交还一个人类可以检查、修改和采用的结果。

本产品不是模型切换器、并排答案列表，也不是自治 AI 组织。长期价值来自这条改进链：

> Objective -> Sources -> Artifact -> Finding -> Objection -> Change -> Verification -> Human Decision

## 产品形态

它仍是一个产品。任务模式定义要完成什么工作；权限等级定义房间可以使用什么工具。

### 任务模式

- **Review：** 根据目标和用户提供的来源，检查并修订已有产物。
- **Decide / Plan：** 比较路径，或生成带风险、成立条件和 checkpoint 的可执行计划。
- **Explore：** 在收敛前扩大可能性空间，包括脑暴和反思型娱乐模板。
- **Create：** 通过创作、编辑审阅和版本化修订，维护连贯的长篇产物。
- **Play：** 运行包含公共与私有 Seat 状态的规则模拟或游戏。它是未来实验 Pack，不是当前优先级。

### 权限等级

- **Discuss：** 只基于用户提供的上下文和持久化房间产物进行推理。
- **Research：** 检索来源、保存时效信息，并把主张标记为有支持、矛盾、推断、过期或未解决。
- **Execute：** 在隔离执行面使用已批准工具，并验证产生的状态变化。

任务模式与权限等级相互独立。Review 可以只用 Discuss，也可以启用 Research；Create 可以使用 Research；Play 可以调用确定性工具，但不会因此获得通用工作区权限。

## 共享核心与任务 Pack

开发由产品线驱动。一层精简共享核心支持多个纵向 Task Pack。

### 共享核心

- provider、model、Connection、Role、Skill 与 Seat 组合；
- 流式调用和验证后 Turn 呈现；
- room、event、state、artifact、version 与 usage 持久化；
- 预算、停止、中断、幂等和人工批准边界；
- 上下文策略和来源链；
- 协议运行与权限执行。

### Task Pack

每个 Pack 自己定义 agenda schema、推荐 Role Pack、阶段协议、新增状态、上下文策略、Artifact 类型、Human Gate 和评测 rubric。Task Pack 不重复实现供应商接入、持久化、计费边界或房间历史。

采用 **Rule of Two**：只有至少两个经过验证的 Task Pack 都需要一个抽象时，它才进入共享核心。此前保留在具体 Pack 内。

## 第一条产品线：Review

Review 是第一条完整纵向切片，因为它能直接检验差异化假设，并产生可与单个强模型比较的结果。

第一版 Review 流程：

1. 人类提供目标、Artifact v1、参考资料和真实性边界。
2. 两到三个任务自适应审阅者独立检查。
3. 系统聚类重复 Finding，同时保留关键冲突。
4. 只有明确的高影响问题获得有限交叉审阅或定向辩论。
5. 指定 Editor 生成结构化 Change Set 和 Artifact v2。
6. 独立审阅者根据目标、来源和真实性边界核验改动部分。
7. 人类逐项接受、拒绝或编辑修改，之后才能批准不可变版本。
8. 房间发布简短摘要、详细产物、已接受 Change Set、未解决问题和用量。

首批 benchmark 是“简历对照职位描述”、产品或需求文档，以及技术计划。简历是有用 benchmark，不是永久市场边界。

## 后续顺序

1. 保留当前 v0.10c 恢复点，并进行一次明确预算的真实供应商 Observer + 定向辩论烟雾评测。
2. 把 Review 做成第一条端到端 Task Pack。同一切片内不扩建 Observer、语义路由、通用 Agent 自治或大范围 UI 基础设施。
3. 在三个 benchmark 上，把 Review 与保存的单模型基线、手动多模型复制流程比较。
4. 构建一条 Decide / Plan 纵向切片，用它验证 Review 中哪些抽象确实应进入共享核心。
5. 收束经过证明的 Task Pack 契约、Artifact 版本、Role Pack、上下文策略和评测 rubric。
6. 只通过有限纵向切片依次加入 Explore，再加入 Create。
7. 当并行来源调查具有明确优势时，在 Research 中引入第一个真正多 Agent 工作流。
8. 只有 Research 与 Human Gate 可靠后才加入 Execute；规划、执行、独立审阅和确定性验证必须分离。
9. Play 作为可选未来 Pack，需要确定性规则、私有 Seat 状态和严格可见性边界。

## 多 Agent 边界

多个模型 Seat 不会自动变成自治 Agent。只有任务可以拆成独立有用的子任务、参与者需要不同工具或私有上下文、输出具有合并契约且结果可以验证时，才加入多 Agent 行为。

Review 首先使用有限模型角色和确定性编排。Research 可以增加 Lead Researcher、并行 Search Worker 和 Citation Checker。Execute 可以在隔离工作区中增加 Planner、Executor、Reviewer 和 Tester。当前产品不以通用自治 Agent 平台为前置条件。

## 方向校正

每个完成的产品里程碑必须回答：

1. 这次修改解决了哪个真实用户问题？
2. 用户最终获得了什么可使用的产物或决定？
3. 一个强模型是否能用更低成本得到同样结果？
4. 哪些关键发现明确来自独立交叉审阅？
5. 增加了多少成本、延迟、阅读负担和复杂度？
6. 如果证据不足，应删除或简化什么？

开发硬规则：

- 不连续进行两个纯基础设施里程碑。
- 每个产品里程碑以至少一个真实案例和保存的基线结束。
- 每个新增付费模型调用在实现前必须写明预期信息增量。
- 不为只有一个已验证使用者的需求创建共享抽象。
- 没有明确用例和 Human Gate，不扩大自治、权限、模型数量或轮次。
- 漂亮 transcript 或可靠状态机不等于更好的用户结果。

## 成功证据

只有结构化多模型审阅产生了单个强模型遗漏、且最终被用户接受的重要改进，同时成本、延迟和人工阅读负担可接受，核心假设才得到支持。

至少跟踪：

- 交叉审阅独有且被接受的高影响修改；
- 错误、无依据或被拒绝的 Finding；
- 根据任务 rubric 得到的 Artifact 质量；
- 达到可采用结果所需时间和人工编辑量；
- 调用、token、延迟和提示性费用；
- 协调、上下文丢失、同质化或“模型一致但没有证据”导致的失败。

不能改善这些证据的功能应被简化、改成可选或删除。

## 明确延后

在 Review 与 Decide / Plan 证明价值前，延后通用多 Agent 平台、模型市场、广泛自定义 endpoint、默认付费 Observer、语义路由器、embedding 基础设施、通用游戏引擎、长篇创作记忆、账号协作和不受限执行。

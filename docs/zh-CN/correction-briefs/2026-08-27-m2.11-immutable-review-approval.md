# M2.11 Correction Brief：不可变 Review 批准

日期：2026-08-27
状态：已完成

## 已观察失败

Review Human Gate 会记录房间级 `approved` 决定，但不会发布一份独立不可变记录，冻结批准时实际可见的 Artifact 版本、Change Set、verification scope 与人工编辑。

## 用户 Artifact

一份不可变的已批准 Review Artifact snapshot：明确批准的是 Artifact v2 还是 v3，保存准确文本和 Change Set，保留模型 v2 verification 结果及 Chair 编辑过的 Change ID，并能从不含凭证的 Meeting History 恢复。

## Baseline

v0.11i 分别持久化 Artifact v2、可选 Human Revision Artifact v3 与房间决定。它们的关系可以推断，但尚未冻结为一份批准 Artifact。

## 最小假设

在现有 approve transaction 中创建一份确定性 snapshot，无需供应商调用或新增协议 phase，就能让批准可审计、可恢复。

## 预期信息增量

不增加模型调用。本切片只验证现有 Review result 与 Human Revision 契约是否足以发布准确批准版本。

## 验收检查

- 只有 Review `approved` 决定创建 snapshot；拒绝不会创建。
- Snapshot 绑定来源 State version 与准确 Review result 创建身份。
- 批准 Artifact v3 时还要绑定 Human Revision 准确时间和被编辑 Change ID。
- 已批准文本与 Change Set 必须和可见 v2 或 v3 结果确定性一致。
- Verification scope 明确模型检查覆盖 v2；批准不能改写 verifier verdict。
- 从 UI 角度，决定与 snapshot 原子保存；存储失败时两者都回滚。
- Snapshot 作为独立不含凭证 Artifact 持久化，旧记录继续可读。
- Build、ESLint、自动测试与 `git diff --check` 通过。

## 成本边界

零供应商调用、零付费 token。浏览器检查只能使用现有本地状态。

## 停止条件

如果不可变批准需要新增供应商 phase、通用签名基础设施、账号身份、云同步或数据库迁移，则停止。加密签名和跨设备权限属于后续范围。

## 结果

本地证据支持该假设。批准 Review 现在会为当前可见 Artifact v2 或 v3 创建带来源的不可变 snapshot，保存准确 Change Set、原模型 verification、人工编辑 Change ID 与批准时间。Snapshot 和房间决定共用现有 durable save 边界；存储失败时，snapshot、决定与协议完成状态一起回滚。拒绝不会创建 snapshot。

Production build、ESLint、`git diff --check` 和全部二十九项自动测试通过。测试会拒绝在当前可见 Human Revision 存在时创建的 v2 snapshot，也会拒绝被修改过 verification verdict 的记录。1280x800 与 390x844 浏览器检查没有页面溢出或控制台警告。本地浏览器仍没有已保存 Review result，因此没有为了布置批准结果 UI 而单独调用供应商。

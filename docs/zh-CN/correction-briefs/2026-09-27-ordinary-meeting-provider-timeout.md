# DP-0.3 — 发言深度改变后的普通会议供应商超时

- **已观察失败：** 用户提供一条 `gpt-5-pro` 提案的 P2 源头回执：`callStatus=timeout`、供应商终态／用量未知、耗时 90,002 ms。普通 `streamProvider` 路径仍有固定 90,000 ms 应用计时器，尽管 Lite／Medium／Uncapped 现要求不同的发言深度和供应商输出上限。
- **用户产物：** 有界的会议调用给较慢供应商合理完成机会，随后要么发布通过校验的发言，要么诚实记录超时；不暗中重试或编造用量。
- **基线：** `PROVIDER_TIMEOUT_MS=90_000` 会中止所有非 Plan 供应商请求。普通房间预算按每回合 90,000 ms 计算；只改请求计时器可能让成功的慢调用在下一阶段被累计时间门槛拦住。截图不能证明供应商本会完成，也不能确定用了多少 token。
- **最小假设：** 普通参与者／总结调用采用有界且随档位变化的应用截止时间（Lite 180 秒、Medium 240 秒、Uncapped 300 秒），房间累计时间预算与相同单回合最大值对齐。其他供应商调用保留既有 90 秒，Plan 保留无应用截止时间。明确 Stop、不自动重试、严格 Turn Envelope 校验和未知回执字段不变。
- **预期信息增益：** 假时钟测试能在零付费调用下验证三个档位的准确中止边界，并证明上层取消、Plan 豁免及其他调用的默认行为。预算 fixture 能证明获准的慢调用不会仅因超过 90 秒就阻挡下一阶段。
- **验收：** 普通三档均不在 90 秒中止，但到声明的有限截止时间仍会中止；取消保持即时；未上报时源头回执仍分类为 `timeout` 且终态／用量未知；房间累计时间不与新单次额度矛盾；`pnpm.cmd check` 通过。
- **成本边界：** 零真实供应商调用，不新增重试、依赖、schema 迁移或部署。等待更久可能增加真实供应商费用和延迟；既有输出 token、回合次数和人工 Stop 边界保留。不宣称模型质量或供应商会完成。
- **停止条件：** 若主机／供应商更早终止，不添加无界 runner，也不从回执推断账单；记录限制，并在另行授权的实际验收之前不宣称截图中的模型现在一定能完成。

## 本地结果

- 普通会议参与者及总结调用采用 Lite／Medium／Uncapped 有限应用截止时间 180／240／300 秒；对应的房间时间额度同步提高。其他调用族保持 90 秒，Plan 仍无应用计时器；没有新增自动重试。
- 假时钟及房间预算测试通过。`pnpm.cmd check` 退出码 0：构建、79/79 离线测试、lint 与生成类型检查均通过。未上报时，既有来源回执仍将供应商终态和用量保留为未知。
- 无付费／真实供应商调用、实时会议浏览器检查、远程 CI、推送或部署。截图定位了旧的本地 90 秒截止，但不能证明延长后一定完成，也不能推断供应商账单。
